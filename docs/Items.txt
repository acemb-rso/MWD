MWD Item Design
================

This document describes the current item model implemented in the MWD system.
It is intended to reflect the live codebase rather than older Anarchy-era
design notes.


1. Core Model
-------------

- All items use a single Foundry document class: `MWDItem`.
- Item behavior is type-driven. The document class is shared; item `type`
  determines schema, sheet, and runtime behavior.
- Canonical item types in `template.json` are:
  - `contact`
  - `gear`
  - `quality`
  - `assetModule`
  - `skill`
  - `lifeModule`
  - `mechWeapon`
  - `personalWeapon`
  - `armor`


2. Shared Item Concerns
-----------------------

Items separate three different concerns. These should not be conflated.

- Descriptive item data
  - Stored directly on `system`
  - Examples: damage, AP, rating, traits, notes
- MWD modifiers
  - Stored in `system.modifiers`
  - Used by the system's roll/modifier pipeline
- Foundry Active Effects
  - Stored as embedded `ActiveEffect` documents on the item
  - Used for runtime effect application when supported equipment is equipped

The live reusable `template.json` item templates are:

- `modifiers`
  - `system.modifiers: []`
- `inactive`
  - `system.inactive: false`
- `references`
  - `system.sourceReference: ""`
  - `system.description: ""`
  - `system.gmnotes: ""`


3. World Items vs Owned Items
-----------------------------

- World items are standalone configuration sources.
- Owned items are embedded in an actor and may participate in:
  - loadout state
  - combat selection
  - equipped effect sync
- Actor-only controls such as equip, primary selection, and direct attack
  should only be available when `item.actor` exists.

  - `isSocial`
  - `listspecialization`

-------

- Templates: `modifiers`, `inactive`, `references`
- Fields:
  - `positive`

Asset Module
------------

- Templates: `modifiers`, `inactive`, `references`
- Fields:
  - `category`
  - `level`
  - `mobility.jumping.*`
  - `targeting.clustering.diceModifier`
  - `targeting.clustering.targetNumberModifier`
- Runtime notes:
  - asset modules may contribute derived machine capabilities instead of direct
    actor fields
  - clustering fire-control upgrades currently aggregate through installed
    `assetModule` items
  - `targeting.clustering.diceModifier` adds cluster dice to attacks that
    already have clustering
  - `targeting.clustering.targetNumberModifier` adjusts the cluster success
    target number; negative values make cluster hits easier

Life Module
-----------

- Templates: `inactive`, `references`
- Fields:
  - `moduleType`

Mech Weapon
-----------

- Templates: `modifiers`, `inactive`, `references`
- This section follows the newer mech-weapon rules direction and overrides
  older schema notes where they conflict.
- Category rules:
  - `weaponCategory` is restricted to `melee` or `ranged`
  - `category` may exist as a normalized mirror of `weaponCategory`
- Skill rules:
  - ranged mech weapons use `gunnery`
  - melee mech weapons use `meleeCombat`
  - no other attack skills are valid for `mechWeapon`
- Damage rules:
  - mech weapons use a fixed base `damage` value
  - `damageType` uses the same damage-type set as `personalWeapon`
  - payloads may contribute `modifies.clusteringDice`
  - payloads may also modify `damageType`, `ap`, and attack-rating bands
  - clustering dice are rolled as `d6cs>=X`; each success adds `+1` damage
  - machine fire-control upgrades may modify cluster dice count and cluster
    target number before the attack resolves
- Payload rules:
  - mech weapons can have multiple payloads, using the same payload-style
    architecture as personal weapons
  - ranged mech weapons may define:
    - `payloads`
    - `selectedPayloadId`
    - `consumptionSources`
  - `selectedPayloadId` is the active payload selection used by the mech-weapon
    sheet and by attack resolution
  - melee mech weapons do not use payloads
- Size field:
  - `size`
- Slot rules:
  - hardpoints define machine inventory slots
  - hardpoints own slot occupancy via hardpoint-level `itemId`
  - mech weapons do not carry hardpoint assignment, hardpoint type, or hardpoint location fields
  - these slot-backed items are separate from machine `assetModule` items and
    separate from upgrade/equipment rails
- Other primary fields:
  - `skill`
  - `damage`
  - `ap`
  - `damageType`
  - `attackRatingBand.close`
  - `attackRatingBand.near`
  - `attackRatingBand.far`
  - `attackRatingBand.extreme`
  - `heat`
  - `volatile`
  - `area`
  - `range.max`
  - `range.close`
  - `range.near`
  - `range.far`
  - `range.extreme`
  - `notes`
- Explicitly not part of the mech-weapon model:
  - `damageAttribute`
  - `monitor`
  - `defense`
  - `noArmor`
- Presentation defaults:
  - default icon: `systems/mwd/img/icons/systems/upgrades/grenade_launcher_underbarrel.svg`

5. Item Sheet Architecture
--------------------------

All AppV2 item sheets derive from `BaseItemSheet`.

Current design rules:

- Item sheets use the MWD shell/theme, not a generic Foundry form
- Item sheets are valid standalone editors for world items
- Actor-dependent controls are ownership-gated
- Item sheets separate the three item concerns into tabs:
  - `Details`
  - `Modifiers`
  - `Effects`

Current implementation state:

- `personalWeapon`
  - layout-driven V2 sheet
  - layout id: `personal-weapon`
  - shared root shell + extracted content partials
- `armor`
  - layout-driven V2 sheet
  - layout id: `armor`
  - shared root shell + extracted content partials
- Other item types
  - still use simpler V2 sheet templates
  - not all are migrated to the layout-driven shell yet

The goal is architectural consistency with the V2 actor-sheet approach:

- thin sheet wrapper
- shared shell
- layout registry driven composition
- named partials for content sections


6. Effects and Equipped Runtime Behavior
----------------------------------------

Embedded `ActiveEffect`s are part of the item model.

Supported equip-sync types:

- `personalWeapon`
- `armor`

Runtime rule:

- the item owns the effect definitions
- the actor is the runtime host of applied effects

Behavior:

- if an owned supported item is equipped, its embedded item effects are synced
  onto the owning actor as actor-side `ActiveEffect`s
- if the item is unequipped, those synced actor effects are removed
- world items never apply effects directly
- item effect create/update/delete reconciles actor-side mirrors when the item
  is currently applicable
- duplicate synced actor effects for the same source item effect are not allowed

Synced actor effects are marked with MWD metadata so they can be reconciled
safely back to the source item/effect pair.

Trait-compatible ActiveEffect keys:

- `system.traitMods.speedMod`
- `system.traitMods.defenseRatingMod`
- `system.traitMods.saCapMod`
- `system.traitMods.faCapMod`
- `system.traitMods.raCapMod`
- `system.traitMods.conditionPhysicalValueMod`
- `system.traitMods.conditionFatigueValueMod`
- `system.traitMods.conditionPhysicalPenaltyMod`
- `system.traitMods.conditionFatiguePenaltyMod`

These keys are a narrow bridge for always-on numeric modifiers from item
effects into derived personal combat state. They do not replace quality trait
packets, which own selectors, optional roll-dialog presentation, phase logic,
conditions, and limits.


7. Combat-Relevant Conventions
------------------------------

Personal combat currently depends on owned item data.

Weapons:

- equipped weapons are owned `personalWeapon` items with
  `system.equipped === true`
- `system.isPrimary` is the first tiebreaker for default weapon selection
- if no equipped weapon exists, attack falls back to a synthetic unarmed profile

Armor:

- equipped armor is owned `armor` with `system.equipped === true`
- `system.isPrimary` is the first tiebreaker for active armor selection
- active armor feeds the actor armor monitor compatibility bridge
- mitigation, defense bonus, and durability are item-driven
- the actor armor monitor tracks damage taken for compatibility with existing
  actor-side systems


8. Design Boundaries
--------------------

The current item design intentionally keeps these separate:

- descriptive item data
- MWD modifier declarations
- embedded Foundry `ActiveEffect` definitions
- runtime actor application of equipped item effects

Items describe equipment and own effect definitions.
Actors host live applied effects and derived combat state.


9. Outdated Concepts
--------------------

The following should not be treated as current source of truth for new work:

- Anarchy-era item type lists such as `trait`, `cue`, `disposition`,
  `vehicleUpgrade`, `mechEquipment`, `vehicleWeapon`, or `weaponGroup`
- older `personalWeapon` field names such as `armorPiercing` as the canonical
  AP field
- assumptions that `traits`, `modifiers`, and `ActiveEffect`s are one system.
  `system.traitMods.*` ActiveEffects are supported as an explicit numeric
  bridge, not as full trait packet behavior

Use the canonical types and structures documented above instead.
